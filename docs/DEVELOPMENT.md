# Reconstruction workflow

GOALS.md defines acceptance. Game source lives in src/, include/, and
config/usa/arm7/src/. Regional symbols, relocations, delink maps, ARM7 source
manifests, and linker metadata in config/ are part of the build contract.

## Iteration and acceptance

1. Select a bounded function family and inspect its declarations, instructions,
   relocations, callers, and data ownership.
2. Compile candidate objects and compare unchanged original targets with
   tools/match_unit.py. Detailed comparison logs stay under ignored build/.
3. After ten unproductive variants, record the evidence and switch dependencies.
Deferred functions remain required work.
4. Run tools/configure.py usa, then ninja rom check report sha1. Preserve all
   coverage denominators and report ARM7 code, literals, data, BSS, necessary
   assembly, and original fallback separately.
5. Use tools/work_batch.py start NAME and finish NAME to record accepted coverage
   deltas and elapsed time. Run tools/verify_clean_build.py --revision HEAD
   --require-sha1 for clean committed milestones. Test relevant gameplay when
   the runtime scope warrants it.

Keep original ROM inputs independent from generated outputs. Shared read-only
inputs can use tools/rom_inputs.py; new bindings live in build/inputs.json.
Existing build/factory/inputs.json bindings remain readable for worktree
compatibility. ROMs, compiler binaries, environments, and generated assets are
local inputs or outputs, never source deliverables.

USA ROM-configuration generation preserves an existing output timestamp only
when the freshly generated bytes are identical. Ninja `restat` avoids rebuilding
unchanged ARM7 source in that case. ROM packaging also depends directly on the
linked ARM9 ELF, so every ARM9 relink still repackages the ROM. Module, symbol,
ARM7, coverage and ROM SHA-1 checks remain part of acceptance.

USA linker-script generation uses the hash-pinned LCF-only DSD profile in
`config/usa/arm9/lcf_tool.json`. The patch indexes section addresses before
ordering, walks the original comparison graph without allocating its edges,
and reuses each module's sorted ownership list when writing
`objects.txt`. It generates fresh outputs on every invocation; it does not cache
scripts or change ordering, gap generation, overlap validation or retention rules.
Other DSD commands use the configured original binary. Binary and patch hash
mismatches fail generation. Ninja tracks the profile, patch and selected binary.
Rebuild the local acceleration with `python3 tools/build_dsd_lcf.py`; the builder
uses the recorded source commit, Cargo lock and immutable Rust container image,
runs the ordering regression test, and verifies the resulting binary hash. A
rebuild requires a fresh `build/tools/dsd-lcf-build/source` directory.

Integration generates the linker script alongside original-target extraction.
Linker alignment uses module-scoped input-section indexes. Link-only ELF mutation
guards compare all unchanged byte ranges and permit only the existing reviewed
metadata edits; original comparison targets remain untouched.

On POSIX builds, object preparation gives the linker byte-identical copies with
short names in `build/usa/short_link`. A matching LCF changes only object selectors;
input order, symbols, section names, alignment and retention stay unchanged. An
atomically claimed temporary directory symlink exposes those workspace-local
copies through a short path while MWLD runs. The helper removes its alias on
success or failure and leaves a stable response file and SHA-256 provenance in
`build/usa/short_link/report.json`. It never reuses an existing temporary name or
writes through symlinked or hard-linked copy files. The original source objects,
including debug metadata used by comparison and function analysis, stay intact.
Native Windows builds keep their original linker invocation. Ninja tracks the
short-path helper as a linker dependency.

Dashboard publication reads a bounded selection of immutable accepted snapshots
and stages only a new snapshot and page. It never copies or rewrites the complete
archive. A snapshot-name collision fails publication rather than replacing
history. Rollback removes transaction-created snapshots and restores the prior
workflow, checkpoint and page while the publication lock remains held.

## Compile and compare in one agent call

For candidate selection, Ghidra batch inspection, source/range preparation,
parallel batch verification, and linked-layout diagnosis, see
[Reconstruction scripts for agents](RECONSTRUCTION_TOOLS.md).

After configuring the build with Wibo and generating the original target objects,
run this command from the project root in a single terminal tool call:

```sh
python3 tools/match_unit.py src/GameState/GhidraWorkflowAccessors --require-match --json
```

Replace the unit name with an exact name from `objdiff.json`. The command builds
the candidate with the configured Ninja compiler runner, then compares it against
the original target using objdiff. Ninja is resolved from the project virtual
environment or PATH; `--ninja PATH` overrides it.

The command returns one JSON result with match status, symbol/mismatch counts,
elapsed time, and an artifact directory. Exit codes are 0 for an objdiff match,
1 for mismatches, and 2 for build/comparison errors. Compilation failure stops
comparison, so a stale object cannot produce a success result. Verbose compiler
and comparison output, candidate snapshots, and per-symbol differences stay in
`build/matching/`. Without `--require-match`, the existing comparison-only exit
behavior remains unchanged.

This is an object comparison, not full ROM acceptance or an independent raw-byte
proof. Run the integrated checks described above before accepting a batch.

## Accepted compiler runtime support

The user authorized matching assembly for identified compiler runtime helpers on
2026-10-10. `config/usa/arm9/runtime_support.json` records the accepted identities,
vendor archives/objects, original source filenames where available, and source
and original-byte hashes. These functions are excluded from C reconstruction by
candidate selection, dependency ranking and candidate preparation. Existing
matching C implementations are retained and labelled as runtime support.

Runtime support now uses CodeWarrior assembly functions in `.cpp` files:
`extern "C" asm void name() { ... }`. This changes the source container, not its
classification: these routines remain accepted assembly and are excluded from
C/C++ reconstruction. `#pragma thumb off` selects their original ARM mode.

Nine branches into shared tails use `RUNTIME_BRANCH(condition, displacement)`
inside a `dcd` directive. The macro expresses the ARM branch condition and PC
relative displacement because the pinned inline assembler accepts a bare branch
label but rejects label-plus-offset expressions. Each site names its shared tail
in a comment. Other instructions use ordinary mnemonics, and embedded literal
and lookup-table data uses `dcd`. Two short shared tails extend their surrounding
source units by 36 bytes while leaving named function extents unchanged.

`normalize_runtime_inline.py` restores exported interior labels, original named
function extents, and mapping-symbol metadata omitted by the inline assembler.
It checks each explicit branch encoding and never changes executable section
contents, literal data, or relocation contents. Original objdiff inputs remain
untouched. Object comparisons, linked-address checks and full ROM SHA-1 checks
remain mandatory. Objdiff reports three nested runtime labels as additional
function records; acceptance verifies those aliases separately while runtime
totals count the 44 named helpers once.

Runtime retention uses the LCF `FORCEACTIVE` directive because MWLD limits its
command-line symbol list to 255 characters. Replacing the previous `.s` sources
uses the existing locked integration gate with a hash-bound runtime replacement
manifest and rollback of both source forms and policy. It earns no new coverage.

Assembly is reported separately from C/C++ coverage. `audit_assembly.py` validates
the accepted source hashes, linked original-byte hashes and report matches before
the dashboard publishes the runtime assembly totals. Runtime policy installation
and rollback are part of the existing global integration transaction.

### SDK support assembly (community reconstruction)

Some matching assembly is SDK code, not a compiler runtime helper, and no vendor
object is available. These routines use `"evidence_class": "sdk_reconstruction"` in
`runtime_support.json`; rows without the field remain compiler runtime. The evidence must state
`origin: community_reconstruction`, `vendor_archive_match: false` and null `library`/`object`;
vendor package fields are refused. It must pin each external source (repository, 40-hex commit,
path, URL, hashed local copy), bind an instruction comparison whose variants equal the original
words, and carry a fresh object check (compile result, raw-byte result and the exact source) for the
integrated source. The original bytes are re-hashed from `extract/usa/arm9/arm9.bin`.
The source lives in `src/RuntimeSupport/*.cpp` (so it is built and coloured as runtime assembly), its
header begins `SDK support (community reconstruction):` and must not use the compiler runtime phrase.

The existing 48 rows are accepted through an explicit append transaction only: a manifest carries
`runtime_append` (not `runtime_support`/`runtime_replacement`), the gate re-reads the accepted policy under
the integration lock, refuses duplicates and non-canonical prior bytes, preserves every existing row and
top-level key byte-for-byte, and restores the prior policy on rollback. Report aliases are verified but not
recounted. The matched assembly bytes and functions enter the binary report like any matched code, but the
receipt books `functions=0`, `code_bytes=0`, `runtime_assembly_*` and `c_instruction_credit=0`;
`work_batch.py finish --runtime-assembly-functions/--runtime-assembly-bytes` records the C gain separately.
Denominators are unchanged. `audit_assembly.py` reports compiler and SDK assembly counts separately.

## Repository boundary

DQIX owns reconstructed source, build configuration, matching tools, technical
analysis, source-coverage baselines, and reproducibility documentation. The
separate Factory project owns orchestration, independent agent review,
scheduling, queues, worker records, dashboards, and token accounting.
Factory's DQIX gates live in adapters/dqix/tools/ and instance records in
projects/dqix/workflow/ within that project. They are not required for a
standalone DQIX build. Upstream GitHub Actions remain repository CI.

Technical inventory, call graphs, function databases, and progress viewers are
optional DQIX development tools. They do not supply game instructions or source
coverage. Verification summaries stay in docs/verification/; verbose logs stay
under ignored build/verification/ (archived logs in its archive/ directory).

### Pinned objdiff ARM parser repair

USA selects the hash-pinned objdiff 2.7.1 repair in
`config/usa/objdiff_tool.json`. The sole ARM parser change is upstream PR359,
commit `e28a2021eb3e669f6011f7645b009f73aa19ddbc`: when an executable section
has no mapping symbols, use the existing fallback instruction modes. This fixes
an out-of-bounds panic without dropping sections or modifying original targets.
The input CLI remains read-only. A newer release was not substituted because its
report accounting differs from the accepted baseline.

Rebuild the ignored binary with `python3 tools/build_objdiff_backport.py`.
The recipe verifies the source archive, Cargo lockfile, exact upstream patch,
Rust 1.85.1 installer/manifest, immutable factory container image, and final binary
hash. Rust/Cargo state stays in ignored `build/tools/objdiff-backport/`.
Configure validates the selected executable and patch hashes; the local
`objdiff-cli` selector points to the same repaired binary for object comparisons.

### Source-owned ELF metadata

Per-source compiler profiles may preserve a documented compiler-emitted tail as
original inventory labels with `normalize_source_extents.py`. The source/compiler
hashes, emitted extent and every byte are checked: the decimal round-up source
owns one80-byte emitted routine represented by the original76+4-byte labels.
No instructions, data or relocations change, and both inventory entries remain.

`partial_link_absolute_symbols.py` applies declared ordinary ELF ABS32
relocations for hash-bound scalar constants from the actual linker policy.
This retains source references to linker-defined SDK stack sizes, whose values
cannot become compile-time constants without changing the original control flow.
Only declared mapped-data relocation destinations change; every other byte and
relocation is retained. Pristine compiler objects and transformation receipts are
saved. Fresh object, linked-layout, module, symbol and ROM checks still apply.

### Retaining executable fallback during source splits

A runtime assembly row can retain an adjacent original executable fallback with
`retained_fallback_code`. The original range, every existing function identity,
mode, extent, byte hash and triggering source hash are verified. Configure and
the pre-link guard retain a validated existing symbol so MWLD cannot discard
the newly isolated section. Retained fallback earns no source or assembly credit
and remains eligible for reconstruction. This is separate from data retention.

Configuration validates retained-code source and map ownership before extraction.
The pre-link guard additionally requires all original range and function byte
hashes after extraction. Acceptance always validates both; fresh configuration
does not require generated extraction files to exist.
